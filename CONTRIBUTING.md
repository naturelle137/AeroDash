# Contributing to AeroDash

Thank you for your interest in contributing! Since this is a safety-critical aviation tool, we have specific development workflows.

Before you start coding, please read our **[Branching Strategy & Workflow Guide](docs/development/BRANCHING_STRATEGY.md)**.

## Quick Summary
* **Never commit directly to `main` or `develop`**.
* Use `feature/...` branches for new code and bug fixes.
* Always open a **Pull Request** targeting the `develop` branch.
* Ensure you use our PR templates and complete all safety checklists.

## Documentation as Code

We use Architectural Decision Records (ADRs) to document *why* decisions are made. 
If you are making a structural change to the product, introducing a new pattern, or changing the developer workflow, please write an ADR.
Read the **[ADR Guide](docs/architecture/adr/README.md)** for details on the numbering scheme and lifecycle.
